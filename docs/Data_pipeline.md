# EventProject Data Pipeline Documentation

**Project:** EventProject
**Dataset:** EVIMO2 v2
**Framework:** PyTorch
**Current Version:** Data Pipeline v1.0

---

# 1. Overview

The data pipeline is responsible for converting the raw EVIMO2 dataset into model-ready tensors while maintaining a clean separation between deterministic preprocessing and experiment-dependent transformations.

The pipeline follows the philosophy:

> **Precompute only deterministic dataset information.**
>
> Anything that depends on model architecture or training hyperparameters is computed online inside the Dataset or Transform pipeline.

This approach provides several advantages:

* reproducibility
* modularity
* low preprocessing cost
* easy experimentation
* minimal storage overhead

# 4. Design Philosophy

The pipeline intentionally separates the responsibilities into four layers.

```
Raw Dataset
        ↓
Preprocessing
        ↓
Dataset
        ↓
Transforms
        ↓
Model
```

Each layer performs only one responsibility.

---

# 5. Preprocessing Stage

The preprocessing stage is executed only once.

```
tools/preprocessing/preprocess.py
```

The preprocessing stage computes only deterministic information.

No model-dependent information is stored.

---

## 5.1 Event Index Cache

Purpose

For every frame, store the event indices belonging to the temporal interval

```
[frame_i , frame_{i+1})
```

instead of searching timestamps every training iteration.

Stored file

```
cache/event_index.npz
```

Contents

```
event_start
event_end
```

Shape

```
(N_frames,)
```

Benefits

* O(1) event lookup
* No binary search during training

---

## 5.2 IMU Index Cache

Purpose

Exactly analogous to the Event Index.

For every frame

```
frame_i
```

store the IMU samples that belong to

```
[frame_i , frame_{i+1})
```

Stored file

```
cache/imu_index.npz
```

Contents

```
imu_start
imu_end
```

Benefits

* Constant-time IMU lookup
* Temporal synchronization with event packets

---

## 5.3 Camera Motion Cache

Purpose

Store camera motion information already computed from the dataset poses.

Stored file

```
camera_motion.npz
```

Contains

* translation
* quaternion
* delta translation
* delta quaternion
* linear speed
* angular speed
* frame interval
* pose availability

Benefits

No pose processing is performed during training.

---

## 5.4 Frame Motion Cache

Purpose

Stores per-object motion between consecutive frames.

Contains

* object ids
* object displacement
* object speed

Dynamic/static classification is **not** stored.

Instead, speed thresholds are applied during training if required.

This keeps preprocessing independent of experimental settings.

---

# 6. Dataset Layer

Main class

```
EVIMO2Dataset
```

Each dataset item corresponds to one frame.

Returned object

```
EVIMO2Sample
```

The Dataset performs only lazy loading.

Heavy data are never kept duplicated in memory.

---

# 7. Returned Sample

Each sample contains

```
Sequence metadata

Frame metadata

Event packet

IMU window

Camera motion

Object motion

Depth

Instance mask

RGB image
```

---

## 7.1 Event Packet

Representation

```
events_xy
events_t
events_p
```

Shapes

```
events_xy

(N_events,2)

events_t

(N_events)

events_p

(N_events)
```

No voxelization is performed inside the Dataset.

---

## 7.2 IMU Window

Representation

```
timestamps

angular_velocity

linear_acceleration
```

Shapes

```
(N_imu)

(N_imu,3)

(N_imu,3)
```

The IMU window always spans the same temporal interval as the event packet.

---

# 8. Temporal Dataset

Main class

```
TemporalEVIMO2Dataset
```

This wraps the frame dataset.

Example

```
history_offsets

(-3,-2,-1,0)
```

returns

```
t-3

t-2

t-1

t
```

The final frame is considered the reference frame.

Only valid temporal windows are generated.

No temporal padding is used.

---

# 9. Collate Function

The DataLoader collate function performs batching.

Unlike the Dataset, the collate function concatenates variable-length data.

---

## 9.1 Events

Events are concatenated into one continuous stream.

```
events_xy

events_t

events_p
```

Additional array

```
event_sample_indices
```

stores which sample each event belongs to.

Example

```
events

e0
e1
e2
e3
e4
e5

sample indices

0
0
0
1
1
2
```

This avoids Python lists while allowing efficient masking.

---

## 9.2 IMU

Exactly the same representation is used.

```
imu_timestamps

imu_angular_velocity

imu_linear_acceleration

imu_sample_indices
```

The IMU representation mirrors the event representation.

Benefits

* identical processing pipeline
* simple masking
* vectorized operations

---

# 10. Transform Pipeline

The Dataset returns raw numpy arrays.

The Transform pipeline converts them into model inputs.

Current order

```
ToTensor

↓

NormalizeEventTime

↓

NormalizeIMU

↓

VoxelizeEvents
```

---

## 10.1 ToTensor

Converts only model inputs.

Converted

* events
* IMU

Everything else remains inside metadata.

Benefits

Avoids unnecessary tensor allocations.

---

## 10.2 Normalize Event Time

For every frame independently

```
first event

↓

0

last event

↓

1
```

Normalization is performed independently for each sample using

```
event_sample_indices
```

---

## 10.3 Normalize IMU

Exactly analogous to event normalization.

For every IMU window

```
first sample

↓

0

last sample

↓

1
```

Only timestamps are normalized.

Gyroscope and accelerometer values remain unchanged.

---

## 10.4 Event Voxelization

Normalized events are converted into voxel grids.

Input

```
events_xy

events_t

events_p
```

Output

```
(batch_size,

num_bins,

height,

width)
```

Current configuration

```
num_bins = 5

height = 480

width = 640
```

Temporal bilinear interpolation is used.

Positive and negative polarities are accumulated in the same voxel grid using signed contributions.

Voxelization is intentionally placed inside the transform pipeline because

* number of bins is a hyperparameter
* interpolation strategy is experiment-dependent
* allows future augmentation before voxelization

---

# 11. Final Model Input

After all transforms

the model receives

```
Voxel Grid

(B,
T,
H,
W)

IMU Sequence

timestamps

angular velocity

linear acceleration
```

Metadata remains attached for

* evaluation
* visualization
* debugging
* loss computation

without being unnecessarily converted to tensors.

---

# 12. Why This Design?

The pipeline follows several guiding principles.

## Deterministic preprocessing

Only information independent of training is cached.

---

## Lazy loading

Large arrays remain on disk until needed.

---

## Modular transforms

Training-time operations remain independent from preprocessing.

---

## Hyperparameter flexibility

Voxelization, normalization and future augmentations can be changed without regenerating caches.

---

## Separation of responsibilities

| Component        | Responsibility                           |
| ---------------- | ---------------------------------------- |
| Preprocessing    | Deterministic caches                     |
| Dataset          | Sample loading                           |
| Temporal Dataset | Temporal window construction             |
| Collate          | Batch construction                       |
| Transform        | Tensor conversion and feature generation |
| Model            | Learning                                 |
